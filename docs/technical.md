# 春风DX：开战按手柄 X 跳过战斗动画

整理日期：2026-11-07；公开维护版：2026-11-08。针对本地已交付的 R30 实现与 R45 标准／X 双版本核对。

## 1. 先看实现结论

在普通战斗的演出条件命令处插入一个 **30 帧等待窗口**，读取游戏自己的手柄状态。发现 X 后，把脚本游标改到原生演出后的公共入口，交由原游戏执行后续战后流程。战斗计算仍由原程序完成；补丁没有自己计算伤害、伪造击坠或直接写奖励。

每场单独判断，不写永久“关闭动画”选项。确认开战时按住手柄 X，或在窗口内轻按 X，都会生效。不按 X 会多等待约半秒，然后恢复原来的条件处理。动画已经开始后再按 X 不生效。这里的 X 是 **SNES 手柄 X**，键盘按键取决于模拟器映射。

本轮确认：R45 X 版保留了与最初 R30 **完全相同的 58 字节代码**。从 R45 标准版生成的结果与既有 R45 X 成品逐字节相同。

## 3. 地址、数据和入口

下表 CPU 地址与文件偏移严格分开。本作这些 ROM 地址按 `file = cpu & $3FFFFF` 换算；这不是其他 mapper 的通用公式。

| 对象 | CPU／WRAM 地址 | 无头 ROM 文件偏移 | 含义 |
|---|---|---|---|
| 原条件处理入口 | `$83:9204` | `$039204` | 原四字节 `C2 30 A5 AC`，即 `REP #$30; LDA $AC` |
| 补丁跳转 | `$83:9204` | `$039204` | 改成 `5C AA 78 FB`，即 `JML $FB78AA` |
| 新代码 | `$FB:78AA..78E3` | `$3B78AA..3B78E3` | 58 字节，末端 `$3B78E4` 不包含在内 |
| 原脚本条件命令 | `$CB:3DA4` | `$0B3DA4` | 已读取操作数后，脚本游标为 `$CB3DA7` |
| 目标脚本游标 | `$CB:3DC0` | `$0B3DC0` | 原生演出后的公共入口 |
| 正常恢复代码 | `$83:9208` | `$039208` | 从原条件处理的下一条指令继续 |
| 脚本游标 | `$7E:0092..0094` | 不适用 | 24 位，小端 |
| 当前脚本命令 | `$7E:00AA` | 不适用 | 原解释器状态 |
| 命令阶段 | `$7E:00AB` | 不适用 | 本命令阶段／补丁临时计数 |
| 原命令操作数 | `$7E:00AC` 起 | 不适用 | 原条件处理仍要使用 |
| 按住手柄位 | `$7E:03EC..03ED` | 不适用 | 本游戏的按住状态副本 |
| 新按手柄位 | `$7E:03F0..03F1` | 不适用 | 本游戏的新按状态副本 |
| X 位 | `$0040` | 不适用 | 对两份手柄状态按位或后测试 |
| 校验和／反码 | `$C0:FFDC..FFDF` | `$00FFDC..00FFDF` | 构建器重算 |

指针门控使用两个重叠的 16 位读取：`[$92] == $3DA7`，且 `[$93] == $CB3D`。后者覆盖 `$93/$94`，所以实际检查了完整三字节 `$CB3DA7`，不是只匹配低 16 位。这样共享的条件处理函数遇到其他剧情条件时，直接回到原逻辑。

当前两组底包→目标均有 **63 个实际字节发生变化**。写入区域容量为 `4 + 58 + 4 = 66` 字节；其中三个机器码字节本来就是 00，所以不能把区域长度当成实际差分数。

## 4. 处理顺序

```text
原生战斗计算（此前的 68/17 命令）
  → 原生演出条件 $CB3DA4
  → $83:9204 被改成尾跳到 $FB78AA
      ├─ 当前脚本不是 $CB3DA7 → 重放 LDA $AC → $83:9208
      └─ 正是本场战斗入口
          ├─ (held | pressed) & $0040 != 0
          │    → $92 写 $3DC0，保留 $94 的 $CB
          │    → 原生命令完成入口，继续战后脚本
          ├─ $AB < 30
          │    → $AB 加一 → 原生按帧等待入口 → 下一帧再检查
          └─ $AB >= 30
               → 重放 LDA $AC → $83:9208 原条件处理
```

原生的伤害、反击、消耗、资金、成长、击坠及后续剧情仍由原程序负责；新代码只改变是否进入演出路径。准确的原生命令流程应以源码和日志为准，不把 `$CB3DC0` 单独理解为一个可随意调用的“万能结算函数”。

### 帧窗口的边界

源码在计时比较**之前**读取 X。无 X 时，阶段值 0..29 各等待一帧，阶段 30 的再次进入先检查 X，再恢复原处理。原日志中是 6901 帧阶段 00，6931 帧阶段 1E，共 31 次入口检查、30 次等待。不能把“30 帧窗口”误读成只访问入口 30 次。

实际历史测试证明窗口第 15 帧短按一帧有效，第 45 帧按下无效；每个临界帧的组合没有逐一做运行验证。窗口大小若改变，不只改一个常数就直接宣称兼容；还要复核原命令阶段生命周期与正常路线延迟。

## 5. 解释器 ABI：为什么是 JML，以及为什么不能改成 RTL

这是对现有命令处理的**尾跳转**。入口由 `JML` 替换原四字节，不额外压入返回地址，新增代码也没有把它当作 `JSL/RTL` 子函数使用。

原入口为 `REP #$30; LDA $AC`。补丁先执行 `REP #$30`，使 A/X/Y 为 16 位；正常回退重新加载 `$AC`，再 `JML $839208`。因此原条件代码接续时有它需要的宽度与操作数。

等待时 `SEP #$20` 仅把 A 设为 8 位，`INC $AB` 因而只更新一个阶段字节。不能在 A16 下直接 `INC $AB`，否则会连同后面的 `$AC` 操作数一起修改。

跳过路径恢复使用 A16，只写 `$92/$93` 两字节，不改 `$94` 的银行字节。游标已严格门控为 `$CB3DA7`，所以得到完整 `$CB3DC0`。

两处 `DC` 指令是 **`JML [abs]` 长间接跳转**，其三字节指针从银行 00 读取。不要把操作数 `$F5F8/$F5FB` 当成直接目标，也不要按当前 PBR=$FB 去解释它们：

| 指针表地址 | ROM 原字节 | 实际目标 | 行为 |
|---|---|---|---|
| `$00:F5F8` | `43 F6 80` | `$80:F643` | `PHK; PLB; SEP #$30; STZ $AA; STZ $AB; JMP $F572`，完成本命令并返回解释器 |
| `$00:F5FB` | `4E F6 80` | `$80:F64E` | `PHK; PLB; JMP $F546`，进入原生帧等待流程，保留当前命令供下帧重入 |

这两段原生代码里的 `PHK/PLB` 会把 DBR 设回 $80。正常回退则仍接续银行 $83 的原处理。补丁不是“所有寄存器与标志无条件保留”的包装器；它服从该解释器的返回约定。历史入口日志记录 `D=$0000`、`DBR=$83`、`S=$0377`。绝对地址 `$03EC/$03F0` 通过银行 $83 的低地址 WRAM 镜像读取；这里不是直接读 SNES `$4218` 等硬件寄存器。

## 6. 58 字节从哪里来

代码区依据是原 R22 的明确分配账及 R23 的资源搬迁记录，详见 `evidence/code-ownership.json`：

- R22 原有预留范围为文件 `$3B6DC0..$3B78E4`（右端不含）。
- R23 把图像 329 的压缩流放在 `$3B6DC0`，压缩长度 2794 字节，到 `$3B78AA` 结束，包含原格式终止标记。
- 解压输出长度 21846 字节，SHA-256 为 `31fcca8fb858bc902bd08fb2cc0944c1129e4656284748b827650a69e50a1940`。
- 剩余 `$3B78AA..$3B78E4` 正好 58 字节，新代码完全放在该尾部。

**不是因为那里全为 00 就认定可用。** 构建器先固定整个输入身份，再解压验证实际资源终点、输出身份与原钩子字节，最后才核对代码槽内容。新增代码后，逐条比较 329 个实际非空机体图像指针的解压结果和终点。

这些地址只适用于本包列出的两组底包。日文原改版、Titans、其他春风版或带头文件不能直接套地址；特别不能把 `$3B6DC0..$3B78AA` 整块覆盖为代码，那里是正在使用的压缩图像。

## 7. 历史运行证据与本轮核验分别是什么

### 原 R30 的 Mesen 2.1.1 验证

以下是已保留记录，日期 2026-10-15，本轮没有重新跑模拟器：

- 普通 SRAM 冷启动后，用声明的机体／坐标／HP 条件从正常 UI 开战，比较 R29 对照、R30 不按 X、R30 按住 X。
- 同 ROM 原生入口检查点只改变手柄输入：第 15 帧短按 X 一帧能跳过，第 45 帧按 X及按 Y 不跳过；之后地图控制正常。
- 正常与跳过路线的 `$7E1000..$7E1FE4` 共 4069 字节记录相同，七组对照逐字节一致。
- 反击实际命中：己方 HP 10000→8432；反击方 EN 200→195。
- 弹药 18→17；击坠后敌 HP 归零，资金与驾驶员成长变化，相关剧情用正常 A 键推进后结果一致。
- 跳过后走原生“存档”菜单，新产生 8192 字节 SRAM；另一个冷启动实例读回，核对资金、成长、敌机记录与 HP。
- 非击坠样本中，R29 按 X 仍在 8120 帧返图，R30 不按 X 是 8151 帧，R30 按住 X 是 7019 帧。这是该条测试路线的记录，不是所有战斗的固定速度。

原验收 JSON 共有 11 个主案例，另附保存后的冷启动读档检查及七组结果等价对照。不是“全游戏／全部攻击方式已测”。MAP 武器、每关每种武器、全部敌方先手路径与硬件兼容没有穷尽验证。

### 2026-11-07 源码交付核验

- 直接读取现存 R45 标准及 X 成品，核对全部差分只在钩子、58 字节代码和校验和内。
- 新便携构建器分别从冻结 R29、R45 标准版在内存中构建，均与对应既有 X 成品逐字节相同。
- 两组 CLI `--check` 通过，分别比较 329 个图像流；错误底包、带头、截断、重复打补丁与同输入输出路径均拒绝。
- Python 生成的 58 字节与原 R30 生成器完全相同；未调用外部汇编器、未新增模拟器回归、未改现行发布 ROM。

R45 的后续文本消费者回归不能代替上述 X 跳过专用测试。本仓库因此同时保留原 R30 专用证据摘要与代码继承／精确成品验证，分开说明其范围。

## 8. 维护与移植时的检查点

若要移植至其他改版，重新定位战斗计算、演出门控和演出后的公共脚本；核对条件函数是否共享、游标何时前移、解释器如何取参数、阶段字节何时归零、DP/DBR/寄存器宽度和原生回调约定。确认新代码的实际所有权和图像边界后，再选择空间。

至少对比不按、按住、短按、超时与其他按键；检查反击、EN、弹数、击坠、奖励、战后剧情、返回地图、保存及冷读档。普通战斗与 MAP 武器要分别查消费者。只看到动画没出现，不能证明结算和队伍数据正确。

公开仓库提供的是可重建源码、地址合同与不含私人进度的证据摘要。原工程的完整运行转储与玩家保存没有公开，历史运行结果不能由无 ROM CI 单独重现；复现新 bug 请按 CONTRIBUTING.md 记录版本指纹和实际操作。
